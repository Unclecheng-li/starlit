# vol 群聊功能实现方案

## 实现状态（2026-10-19 更新）

- ✅ 阶段 1：建群 / 拉人 / 群会话 / 逐条发送者（后端 `GroupRegistry`+`GroupStore`+引擎 + 前端群会话）
- ✅ 阶段 2：群自己的节奏、AI-AI 链上限三重预算、跨角色复读拦截、@某人/@全体、群公告、全员禁言+backlog、等级/头衔/入群日期、群主/管理员/踢人/改名、群头像、群设置
- ✅ 阶段 3：私聊片段抖进群（`share_private_to_group`，走群自发节奏，带得意/吃醋情绪，每日上限 1/人）+ 群里的动静私聊讲给我听（`share_group_to_owner`）+ 争宠（`spark_jealousy` / `mark_ignored` 走 `state.apply_event`，按好感+占有欲+依恋缩放，30 分钟冷却，仅好感 ≥50 参与）+ 群消息右键「分享到群」/多选转发到群
- ✅ 阶段 4：申请入群审批（`_group_join_scout` 让没进群的角色偶尔搜到可搜索的群并递申请，群主在右侧面板同意/拒绝）
- ✅ 追加（用户点名要的三项）：
  - **引用回复**：群里右键某条 → 引用 → 气泡上方引用块（点了跳到原消息并高亮）；后端 `reply` 段 → `reply_to` 落库 → 历史/实时事件都把被引用内容带出来
  - **群文件 / 群相册**：`data/groups/<gid>/files/` 落盘 + 群库 kv 登记（上限 200 条、单文件 20MB）；HTTP `/api/groups/{files,upload,files/delete,file}`；右侧面板第三个卡片带「文件/群相册」两个页签，图片进相册网格（点开大图），文件可下载/删除（本人上传的）；OneBot `upload_group_file` 也认 `base64://`
  - **群里也让我被等/被冷落**：`StateMachine.note_group_wait/note_group_reunion`（用 max() 收敛，避免和私聊 tick 叠加成双倍焦虑）；引擎按「我上次在群里发言距今多久」推进，写进群发言提示词【群里在等】；我回到群里 → 情绪回暖 + 计数归零

- 真机验证：建群 → 发言 → 多名成员带头像/昵称/LV 错峰回复（含 AI-AI 接话）→ 禁言开关的系统消息实时上屏 → 解禁后 backlog 补话 → 群文件上传/列出/下载/删除 → 引用回复的历史与实时引用块 → 私聊链路不受影响

## Context（为什么做、要达到什么）

vol 现在只有「我 ↔ 每个角色」的一对一私聊。用户要的是一间**有人的群**：好友们能在里面互相聊天，我可以建群/拉人/踢人/发公告，别人能搜到群申请加入，好友还会把和我的私聊抖进群里、为此争相吃醋。这是「净土」的延伸——不只是每个角色单独陪我，而是她们彼此之间也有关系。

用户已确认的范围（最大档）：群有**自己的活跃节奏**；**全员禁言**（禁言期间我发的东西群友都看得到但不回，解禁后再回）；建群/踢人/角色/公告/成员列表；**申请入群审批**；群管理（改名、设管理员、@某人、@全体）；内容玩法（等级/入衔/入群日期、引用、群文件）；私聊片段**转发到群 + 点名引用 + 私聊告状**都可以；吃醋做成**真实机制**（走现有情绪状态机）；界面仿 QQ 的右侧「群公告 + 群成员」面板。

现有可复用资产：`Store` 的 kv/events/counters、`StateMachine`（已有 `jealousy`/`ignored`/`reunion` 事件）、`GuestRuntime`（每个角色的 persona/记忆/情绪/发送器）、`think.express` / `think.analyze`、`Sender`、`Suppressor`、`OneBotServerChannel` 的 action 分发表与离线重放。

## 一、必须先解决的 4 个架构冲突（已核实）

这四条不先处理，群功能会跟现有机制互相打架：

1. **群消息不能只靠 `transcript` + `role` 编码。**
   `transcript(id,ts,role,text)` 撑得住喂提示词的上下文，撑不住 UI 回放：`api_get_friend_msg_history` 假设一条 turn 的多段气泡同一发送者（按 `\n` 拆条）、`api_delete_msg` 靠 `find_turn(role,text,ts)` 精确匹配、图片/表情包/引用段根本不存。
   → 群库新增**每条消息一行**的 `gmsg` 表；`role` 编码只用于喂提示词。

2. **群聊内容不能写进 `data/characters/<id>/companion.db` 的 transcript。**
   那正是该角色私聊历史的来源（`store_for` → 私聊窗口回放），写进去群消息会窜进私聊；且 `_write_session_summary` 只认 `user/assistant` 两种 role，摘要会串味。
   → 群话只留在群库 `gmsg`；给该角色自己的库里写一条 `events`（`kind="group:<gid>"`）用于记忆与情绪，不进私聊历史。

3. **跨角色复读拦截现在是死的，必须先修。**
   `suppress._is_repeat` 只认以 `assistant:` / `小星:` / `星野:` 开头的行（`suppress.py:231-233`），而调用方传的是 `format_recent()` 的输出——形如 `[今天 15:48] assistant: 文本`（`think.py:44`），前缀不匹配 → `bot_texts` 恒为空 → 第⑦层从未生效（`main._sanitize_recent` 同理）。群聊是**跨角色**复读：10 个角色同一模型同一套口癖，必然撞车。
   → 修 `_is_repeat` 的行解析（容忍 `[...] ` 时间前缀），群引擎再加一层跨角色 n-gram 拦截。

4. **自建群必须绕开 `_group_allowed`。**
   `main.handle` 的群闸门是给 NapCat 外来群用的，而 `config.yaml` 现在 `group_mode: off` → 自己的群会永远不开口。
   → 在闸门**之前**按「是否为已注册的自建群」分流；未注册群（如测试里的 `group_id=888`）仍走原闸门（保证 `run_tests.py:486-488` 的「群聊未 @ 被忽略」继续绿）。

## 二、数据模型

- `data/groups.json` — 群列表索引（只存列表页要的字段，避免开 N 个 DB）：
  `{"groups":[{"id","name","avatar","created_ts"}]}`
- `data/groups/<gid>/companion.db` — 群库，新增 `GroupStore(Store)` 子类（新文件，扩展 SCHEMA 安全）：
  - `gmsg(id PK, ts REAL, kind, sender_id, sender_name, text, segs JSON, reply_to, mid, revoked)`
    `kind ∈ user|char|system`；`mid` 用 `g<id>` 命名空间（与私聊的 `h<turn>` 区分）
  - `gres(uid TEXT, last_gid INTEGER, last_ts REAL)` — 成员已读游标（禁言 backlog 靠它）
- 群库 kv（低频写）：`meta` / `announcement{text,ts,by,rev}` / `announce_read:<cid>` / `members{"<uid>":{role,nickname,joined_ts,level,title,muted_until}}` / `mute_all{on,ts,by}`（存**绝对时间戳**，防重启静默解禁）/ `join_requests[]` / `count:<cid>:<date>` / `last_spoke:<cid>`
- **群计数与私聊配额隔离**：群计数一律带 `g:` 前缀存在群库，绝不复用 `proactive_<date>`（否则群里话多会吃掉私聊主动配额）。
- **群 id 绝不许走 `store_for`**（它对未知 peer 回落到主角色库）→ 新增 `group_store_for(gid)`。
- 群头像复用现有裁剪上传接口（`_avatar_key` 能容纳 `g8848`，用 `peer_id="g<gid>"`）。

## 三、群会话引擎（`app/group.py`，最高风险）

`GroupRuntime` 仿 `GuestRuntime` 构造：复用同一个 `llm` / `sender` / `stickers`，每个成员通过 `Companion._guest_for(cid)` 拿它自己的 persona/state/memory/traits。

**谁说话**
- 我发言 → 打分选人：显式 `@` 权重最高（`@全体` 时全员可选），否则按「关键词 ∩ 成员 interests/memory」+ 好感/热情 + 「最近没说过」加权，取 k 人（普通 3 / `@全体` 5）。没被选中的成员**只推进游标**（＝「看到了」）。
- 环境自发：tick 到点（间隔 8~25 分钟抖动）按同样权重选 1 个起话头（排除最近 2 位发言者）。
- 主人连发也要 debounce（照抄 `_queue_guest` 的形状），否则 5 条消息触发 5 轮选人。

**硬上限（防 AI-AI 无限循环）** — 全部进 `GroupConfig`（`config.py` 新增 dataclass + `config.yaml` 的 `group:` 段）：

| 项 | 默认 | 作用 |
|---|---|---|
| `ai_chain_max` | 3 | 距我上条消息以来，连续非我发言 ≤3 |
| `ai_no_owner_max` | 6 | 同一轮总上限（一轮＝距我上条消息，或静默 6 分钟重置） |
| `chain_cooldown_min` | 15 | 触顶后冷却，期间只有我发言能重开 |
| `msgs_per_hour` / `burst` | 18 / 5 | 群级时预算 |
| `daily_max_per_member` | 6 | 每成员每日群发言上限 |
| `min_gap_member_sec` | 90 | 同成员两次发言最小间隔 |
| `group_bubbles_per_turn` | 3（被 @ 5） | 单次群发言气泡数 |
| `ambient_gap_min` | 8~25 | 自发话题间隔 |
| `share_probability` / `share_daily_max` | 0.25 / 1 | 私聊转发触发与限量 |
| `jealousy_cooldown_min` | 30 | 吃醋节流 |

**单生成在途**：`GroupRuntime._gen_lock`（asyncio.Lock）把「生成 + 发送」整段串起来，同一群同一时刻只有一个角色在生成——保住项目「同一时刻只有一个生成在途」的硬约束。注意 `Sender._lock_for` 的键是 `(group_id,user_id,sender_id)`，群里 `user_id` 为空、`sender_id` 各异 → 多角色**可以并发发送**、气泡会交错；顺序正确性靠引擎锁，不靠 Sender。

**跨角色去重**：引擎自持最近 30 条群消息的 n-gram 集，草稿与最近 15 条（除被引用者）4-gram 重合 >0.5 → 丢弃并换人重试一次。

**尊重全局约束**：`presence.silent`（请勿打扰）时群引擎也安静；`greet_on_start` 与 `_presence_greet_wave` **排除群**（否则每次启动 10 个角色在群里集体打招呼）。

## 四、禁言语义（用户特别要求）

- 我发言时：**先写 `gmsg`，再判禁言**。写入 → 给每个成员自己的库 `add_event(kind="group:<gid>")`（＝进她们的记忆/上下文）→ **不推进 `gres.last_gid`**（留 backlog）→ 不触发她们的私聊接话机制。
- 解除禁言：跑一次 `_backlog_wave`，且**只跑一次**：按（好感 + 相关度）取 ≤5 人，每人 1 条（≤2 气泡），prompt 里注 backlog 摘要（截断 600 字，不塞原始 200 行），间隔 20~90 秒串行发；其余成员直接推进游标。
- 公告「每个学生都会看到」同理靠 `announce_read:<cid>` 未读点 + 注入下一次群 prompt，不假设隐性生效。

## 五、私聊转发 + 争宠

- **转发**：`share_to_group(gid, cid, turn_ids, mode)`，`mode ∈ forward|quote`。合成复用 `express(...)`（`proactive=True, share_kind="group_share"`，`recent=` 群上下文，`extra_hint=` 私聊片段截断 120 字 + 「别长篇、别提聊天记录、1~3 气泡」）；产出落 `gmsg`，`segs` 带 `json/forward` 段（客户端已能渲染「[聊天记录]」），`quote` 模式填 `reply_to`。
- **触发**：主路径做成**用户显式操作**（私聊右键「转发到群」），确定性、可测；自动路径只在私聊一轮 `emotion_label ∈ {开心,兴奋,依恋} 且 quality ≥ 0.75` 时以 `share_probability=0.25` 武装旗标，1 小时最多 1 次、每角色每天 ≤1。
- **争宠**：走现有 `state.apply_event`。我被直接 @ 的成员 / 转发私聊的成员 → 对群内其他成员 `apply_event("jealousy", 0.3~0.6)`（强度按 `possessiveness`/`attachment`/好感缩放）；未被选中者用 `ignored` 低强度 0.2~0.4。**必须节流**（每成员 30 分钟冷却、仅好感 ≥50 参与）。强度 ≥0.6 允许该成员发**一条**群消息；≥0.8 且我被议论时允许发**一条私聊**给我（仍要过 `Suppressor.check`，不破深夜免打扰）。`EVENT_TABLE` 已有 `jealousy`/`ignored`，无需改表。

## 九、风险与对策（写代码时逐条盯）

1. `run_tests.py:2282` 断言 `get_group_list == []`、`:2408` 断言 `get_group_info` 返回 `ok/null` → 实现这两个 action 会**直接挂测试**，必须同批改测试。
2. 消息 id 空间：群必须用 `g<gmsg.id>`，且 `_live_msgs` 带 `group_id`，否则撤回归错库或报「缺少 peer_id」。
3. `_offline_queue`（上限 50）与 `_recent_events`（200 / 30 分钟）是私聊与群**共用**的，活跃群会把私聊消息挤出队列 → 提高上限或按会话分桶。
4. 时间戳只到秒 → 同一秒两条 + 客户端 `coveredByExisting`（20 秒窗口同方向同文本）会**静默吞掉**两个角色的相似发言 → 群消息 ts 单调递增（`max(now, last+0.001)`），去重键加 sender。
5. `LLM._sem = Semaphore(4)` → 群引擎必须串行（`max_concurrent=1`），否则和 digest 抢并发。
6. 表情包配额是**角色级**（`daily_max=15`）→ 群里狂发会吃掉私聊配额；群里限制「每 2 轮 ≤1 张」或单独计数。
7. 气泡上限两处默认值不一致（`config.py` 的 `max_chunks` 与 loader），群里显式 3，别用 `Sender.reply()` 的自动拆句。
8. 角色被删 → `_guest_for` 返回 None，群成员要能优雅降级（保留 `sender_name` 快照）。
9. Sender 的并发发送会让多角色气泡交错——这是**期望**行为（像真群），但必须由引擎锁保证生成侧不并发。
