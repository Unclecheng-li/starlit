- **调研时间**：2026-10-12

## 0. 先给结论

**推荐路线：把「大脑」和「通道」彻底解耦。**

```
┌────────────────────────────────────────────┐
│  通道适配层（可换）                          │
│  官方 QQ Bot 插件（合规） / NapCat 小号（全功能）│
└──────────────────┬─────────────────────────┘
                   │ OneBot 11 / 内部事件总线
┌──────────────────▼─────────────────────────┐
│  伴侣核心服务（自建，Python 常驻）             │
│  ① 情绪状态机  ② 记忆层  ③ 主动性调度          │
│  ④ 主体性任务流  ⑤ 双通道生成  ⑥ 表情包/视觉     │
└────────────────────────────────────────────┘
```

理由：
1. 你的 6 条需求里有 4 条（情绪、主体性、主动性、多模态）都在「大脑」侧，与 QQ 无关。先解耦，后面换通道不用重构。
2. **QQ 通道有硬约束**：官方 QQ Bot 文档明确写了「如果用户最近没有互动，QQ 可能会阻止机器人主动发起的消息」。这直接冲击你的第 4 条需求。所以通道必须可换，不能让核心逻辑绑死在官方通道上。
3. 现成轮子很多（OpenClaw / Chatter / 小柚 / AIRI），**不要从零造**。骨架用现成的，只自研「情绪状态机 + 主动性抑制链 + 主体性任务流」这三块——这三块是市面方案做得最薄、也最贴合你需求的地方。

## 1. 需求 → 技术拆解

| # | 你的需求 | 对应技术模块 | 真正的难点（不是表面那个） |
|---|---|---|---|
| 1 | 感性，抓住对话情绪 | 情绪识别 + **情绪状态机** | 情绪必须**存下来、会衰减、影响下一轮**，只写在 prompt 里 = 假情绪 |
| 2 | 理性，能分析对话 | **双通道生成**（分析 Agent + 表达 Agent） | 两种语气不能互相污染；分析结果要结构化，不能是"我感觉他有点难过" |
| 3 | 主体性、有边界喜好、有自己生活、自主上网、选择性分享 | **持久化人格状态 + 后台自主任务流 + 分享抑制** | "自己的生活"必须由**后台任务**产生，靠对话触发的一定是假的 |
| 4 | 主动找我说话 | **心跳调度 + 多层抑制链** | 难的不是"能发"，是"**该不该发**"；乱发比不发更伤体验 |
| 5 | 多模态：识图、懂表情包、自己发表情包 | VLM + **表情包向量检索** | 中文梗/表情包的语义检索，通用 VLM 抓不住 |
| 6 | 接入 QQ | 官方 QQ Bot 插件 / NapCat | **主动消息会被官方拦**；第三方协议有封号风险 |

## 2. 分模块方案对比

### 2.1 QQ 接入层（第 6 条）

| 方案 | 性质 | 支持范围 | 主动消息 | 风险 | 适合 |
|---|---|---|---|---|---|
| **OpenClaw + `@openclaw/qqbot`** | 官方插件，走 QQ Bot 官方 API（WebSocket Gateway） | C2C 私聊、群 @、图片/语音/视频/文件、内置 STT/TTS、多账号 | ⚠️ 官方文档明说**可能被 QQ 拦截**（用户近期无互动时） | 需实名认证 | **主线选择** |
| **NapCat + OneBot 11**（+ NoneBot2 或自写服务） | 第三方协议客户端（逆向 NTQQ） | 几乎完整客户端能力：私聊/群聊/加好友/任意媒体 | 自由，随时可发 | **封号风险**，协议可能随 QQ 更新失效 | 全功能实验，务必用小号 |
| 官方 QQ 频道机器人（botpy） | 官方 SDK | 主要限频道场景，私域有限 | 受限 | 低 | 不适合本项目 |

来源：
- OpenClaw QQ Bot 官方文档：https://docs.openclaw.ai/zh-CN/channels/qqbot
- QQ 开放平台：https://q.qq.com/
- NapCat：https://github.com/NapNeko/NapCatQQ
- 第三方协议风险提示（多篇社区教程一致）：「非官方接入，理论上存在被封号的风险。建议用小号，不要用主力 QQ 号」

**官方通道关键细节（摘自官方文档）**
- 安装：`openclaw plugins install @openclaw/qqbot`
- 配置：`openclaw channels add --channel qqbot --token "AppID:AppSecret"`
- 目标格式：`qqbot:c2c:OPENID`（私聊）、`qqbot:group:GROUP_OPENID`（群）
- 群聊默认要求 `@` 提及，可配 `requireMention: false` 改为 always
- 支持 `dmPolicy/groupPolicy` 允许名单，防止别人乱用
- 流式：`streaming.mode: "partial"`，私聊可用 QQ 官方 `stream_messages` API
- 语音：配 TTS 后，回复里写 `[[audio_as_voice]]` 会合成并发原生语音消息
- **不支持**：消息表情回应（reactions）、话题串。频道场景不支持语音/视频/文件/本地图片

> 注：C2C 私聊 + 图片 + 语音已经够做陪伴机器人了。表情包按**图片消息**发送即可（不受"表情回应不支持"影响）。

### 2.2 双通道对话引擎（第 1、2 条）

思路：**一条消息进来，先理性分析，再感性表达。**

```
用户消息
  ├─► [分析通道] 结构化输出 JSON
  │      { 意图, 情绪: {标签, 强度, 效价}, 潜在需求,
  │        关系信号, 风险(自伤/极端), 建议回应策略 }
  └─► [表达通道] 读上面 JSON + 人格状态 + 记忆 → 生成回复
```

要点：
- 分析通道建议用**便宜快**的模型或小模型，输出严格 JSON（可加结构化输出约束）。
- 表达通道用主力模型，吃「人格卡 + 情绪状态 + 检索到的记忆 + 分析结论」。
- 若要"更理性"的第二种人格：不必换模型，换一份 system prompt + 独立的情绪状态副本即可，成本更低。

直接参考实现：
- **心语 Emotional Chat**（开源，MIT）：情感与意图识别 + 危机安全策略 + 长期记忆 + RAG + Agent 技能 + 多模态，后端 FastAPI + LangChain。https://reporank.net/en/repo/congde-emotional-chat.html
- **Chatter**（ncatbot，QQ 群聊角色扮演）：情绪系统（valence / energy / social_battery）+ 三层记忆 + 六层主动发言抑制链 + 延迟发送模拟人类节奏。非常值得抄结构。https://github.cc/PingGuoLiZiJvZi/ncatbot-chatter

### 2.3 情绪状态机（第 1 条的真身）

**只做"情绪打标"是不够的。** 你要的是"会开心也会难过"，那就必须有一个**独立的、会随时间演化的状态**。

三条可选技术路线：

| 路线 | 做法 | 代表项目 | 评价 |
|---|---|---|---|
| **离散标签 + 数值档** | valence(-100~100) / arousal / energy / social_battery，事件加减 + 时间衰减 | Chatter；hello-agents 好感度系统 | **推荐起步**，最好懂、最好调 |
| **多层关系数值** | 信任/安全感/亲密/依恋/占有欲 五维 0-100，受大五人格与心情调制 | NarratorAI 声悦 https://github.com/dandan1232/NarratorAI | 关系感最强，适合长期陪伴 |
| **微分方程 / 神经递质** | 用依恋理论建模，情绪由方程自然涌现（不是脚本） | Emergent Psychology Engine https://github.com/b3rs3rk1ng/emergent-psychology-engine ；neurostate-engine（6 种神经递质 + 6×6 交互矩阵） | 最有"活人感"，但调参成本高 |

**Emergent Psychology Engine 的「TERROR 效应」值得一看**：用户消失后，焦虑按 `dAnxiety/dt = 衰减 + 50*(神经质/100)*威胁 + 40*(依恋/100)*(1-接触)` 增长，而不是靠 prompt 写"我想你"。这是把情绪做成**系统**而非**台词**的范例。

学术侧（2026 前沿，供以后写论文用）：
- EGMF：专家引导的多模态情感融合 + LLM，中英双语验证。arXiv:2601.07565
- Light-MER：把 8B 情感理解蒸馏到 **<1B**，参数与 FLOPs 降约 11 倍，性能反超教师。ACM MM 2026，https://github.com/GAIR-Lab/Light-MER
- MVFA：参数高效的多模态情感适配器，ChatGLM3-6B 为骨干。https://github.com/Overwhelm1208/MVFA

> 建议：**状态机自建（数值 + 衰减 + 事件），情绪识别调 LLM 或小模型**。别一上来上微分方程。

### 2.4 长期记忆

| 方案 | 架构 | LongMemEval | 评价 |
|---|---|---|---|
| **Mem0** | 向量 + 图 + KV 混合，自动抽取事实 | 49.0%（图能力在付费档） | 上手最快，生态最大（~48K star），适合**起步** |
| **Zep / Graphiti** | 时序知识图谱，带事实有效期窗口 | **63.8%** | 时序推理强（"他以前喜欢 X，三月改成 Y"），需自管图数据库 |
| **Letta（原 MemGPT）** | OS 式分层：core 常驻上下文 / recall / archival | — | 适合超长生命周期 Agent，但整套运行时偏重 |
| 轻量自建 | SQLite + 向量库（Chroma/Qdrant）+ 结构化用户画像 | — | **最推荐给自己用**：无依赖、可控、看得见 |

来源：https://baeseokjae.github.io/posts/best-ai-agent-memory-frameworks-2026 、https://particula.tech/blog/agent-memory-frameworks-tested-mem0-zep-letta-cognee-2026

实践上，陪伴场景真正要的是**三层**：
1. **画像层**（长期稳定）：称呼、忌口、生日、雷点、喜欢的梗
2. **情节层**（事件）：某天发生了什么、当时的情绪
3. **情绪层**（记忆带情绪权重）：哪件事让你开心/难过 → 影响情绪状态机

Chatter 的「未读 → 已读 → 待浓缩」三层 + NarratorAI 的 `emotionalMemories` 都是这个思路。

### 2.5 主动性与心跳（第 4 条）

**核心认知：难的不是"能发"，是"该不该发"。**

学术上这块已经成体系：
- **Proactive AI: From Turns to Replannable Dialogue Timelines**（arXiv:2610.05159）——把交互当作**可重规划的时间轴**，未发送的消息是**可修订状态**。关键原则：**"到期不等于授权发送"**，每条计划中的消息在真正送出前，必须用当前上下文重新判断。这条直接对应"防止定时任务发出一条时过境迁的尴尬消息"。
- **Foundations of Proactive Agents**（arXiv:2609.37267）——提出 3T：Task Capability / Temporal Allocation / **Trust**。有人类实验（30 人）：**干预时机不对时，即使结果正确，信任也会明显下降**；且用户**更偏好 sleep-time（睡眠时段）处理**，即使质量略差，也不愿被打断。
- BAO（arXiv:2602.11351）：agentic RL，用行为增强 + 行为正则抑制冗余交互，平衡任务表现与打扰成本。
- ProACT（arXiv:2607.03730）：breakdown-aware，先诊断"该不该说话"，再选干预技能。

工程侧可直接抄的：
- **阿米娅 QQ 陪聊作品（阿里天池）**：用 cron 做心跳，`everyMs = 12600000`（3.5h）+ HEARTBEAT.md 里 **1 小时随机偏移** → 实际 3~4h 随机触发区间，**避免固定时间的机械感**。消息里串了免打扰校验、连续未回复计数、分层内容生成、表情包匹配、发送、计数更新。https://tianchi.aliyun.com/forum/post/1020835
- **Chatter 的六层抑制链**：时间 → 能量 → 社交电量 → 频率 → LLM 意图判断 → 发送前检查。**这就是"主动但不烦人"的标准答案。**

建议的抑制链（照抄 + 微调）：
```
① 免打扰时段？（睡觉/上班 → 静默）
② 距上次发言多久？(< X 分钟 → 放弃)
③ 连续 N 次没回？(≥3 → 拉长间隔，而不是更频繁)
④ 社交电量是否够？(energy < 阈值 → 放弃)
⑤ 现在真有话说吗？(LLM 判断：有话 → 说；没话 → 静默，允许"今天就不发")
⑥ 送出前最后一遍：这条消息现在发还成立吗？（时过境迁检查）
```

> ⚠️ **通道约束**：如果走官方 QQ Bot，主动消息可能被 QQ 拦（官方文档原话）。所以「主动找人」这条要么接受不确定性，要么用 NapCat 小号承担。

### 2.6 主体性 / 自主上网 / 选择性分享（第 3 条）

这是最有意思、也最少现成轮子的一块。核心参考：

**《AI 需要有自己的人生》** https://ckc.akashio.com/chiral_data/1ac8797316

它的方案非常务实，几乎就是你的需求说明书：
1. **赋予感知**：接搜索 API + 网页浏览 API，让 Agent 能"看见"世界
2. **创建独立任务流**：`DailyDigest()` 定时任务，后台独立跑，不靠用户触发
3. **基于兴趣的静默自主学习**：读什么由它自己决定——**从聊天记录里分析出"你和它最近的共同兴趣点"**，据此搜最新资讯
4. **关键在于静默**：不是跑来邀功说"主人我今天学了 5 个知识点"，而是**向量化后静默存入"你和它"共有的记忆库**
5. **在场与缺席的艺术**：你偶然聊到某话题时，它自然地"也知道这件事"，而不是生硬掉书袋
6. **选择性分享** = 分享抑制策略：不是每次学到东西都分享，而是攒到"值得说"的时候才说

技术组件：
- 后台调度：cron / OpenClaw Cron（`jobs.json`）
- 自主浏览：Web 搜索 API + 无头浏览器（agent-browser / Playwright）
- 兴趣图谱：从对话记忆里抽取关键词 + 实体，聚成兴趣向量
- 选择性分享：一个独立的"值不值得说"打分器（新鲜度 / 与你相关度 / 与上次分享的间隔）

**边界与喜好**怎么做：
- 写进**人格卡**（persona.md），且**可被状态影响**：心情差时话少、不喜欢的话题会明确说"我不想聊这个"
- **边界是"会表达不满"**，不是"永远顺从"——这一点很重要，下面「风险」里会再提
- 参考 AIRI 的人格/记忆分离设计：https://github.com/moeru-ai/airi （记忆系统 Alaya 仍在开发中）

**理论底座**：Stanford Generative Agents 的 memory stream（观察流 → 反思 → 规划）依然是"AI 有自己的生活"的标准范式。

### 2.7 多模态：识图 + 表情包（第 5 条）

**识图（看图、看表情包内容）**
- **Qwen3-VL** 是当前中文场景最优解：2B / 7B / 8B / 72B 全系，中文 OCR 与图像理解强，2B 版针对 CPU 优化（Docker 一键跑），7B 有 GGUF 可用 Ollama / llama.cpp / vLLM。https://localaimaster.com/blog/qwen-3-vl-local-setup
- 已有实战文《Qwen3-VL-2B 入门实战：10 分钟教会 AI 看懂你的表情包并吐槽》，可直接照做。

**理解表情包（这一步光有 VLM 不够）**
通用 VLM 抓不住表情包的"梗"。正确做法是**表情包库 + 向量检索**：
- **MemeMatch**：CLIP 图像编码 + M3E 中文文本编码，4600 张梗图，检索 < 0.3s，Top-2 准确率约 85%，还支持"找不到就生成"。架构可直接抄。http://togithub.com/SakuraTokoyomi/memematch
- **PerSRV**（WWW'25，清华）：个性化表情包检索，微调 LLaVA-1.5-7B 生成"像人写的"表情包语义，微信数据集 **543,098 个候选**。论文：https://arxiv.org/html/2410.21801v2
- **A Template Is All You Meme**：建了 KYMKB（5,200 模板 + 54,000 实例），结论是**模板本身承载了大部分语义**——所以"先认模板，再读文字"比"直接看图"准。
- **QRC 框架**（USC + Adobe）：遇到新梗先搜索网络补背景知识，再解释，对新梗准确率提升 22.5%，小众社区梗提升 34%。

**发表情包（QQ 侧）**
- 通过图片消息发送即可（`sendMedia` 路径，5 MiB 以上走分块上传）
- 表情包源：自建库（推荐，可控且个性化）/ 免费表情包搜索 API（NarratorAI 用的是 tangdouz API）
- 发不发的判断：情绪 → 检索候选 → 一个"该不该插图"的小决策（参考阿米娅：日常 25% 概率、闹脾气 30% 概率触发）

```
   │  └─────────────────────┘  │ · 选择性分享决策  │  │
   │                            └─────────────────┘  │
   │  存储：SQLite(状态/画像) + 向量库(记忆/表情包)     │
   └─────────────────────────────────────────────────┘
```

**分层原则**：感知 → 状态 → 认知 → 行动，自主层并行。每一层都可单独替换、单独测。

## 5. 分阶段落地路线

| 阶段 | 目标 | 交付 | 关键验证 |
|---|---|---|---|
| **0** | 通道打通 | 官方 QQ Bot 能收发文本、图片 | 私聊能互通、图片能收到 |
| **1** | 能聊（有条人设） | 人格卡 + 短期上下文 + 基础记忆 | 连续聊 30 轮不崩人设 |
| **2** | 有情绪 | 情绪打标 + 数值状态机（衰减/事件） | 骂它 / 夸它，状态数值确实变化且影响下一轮语气 |
| **3** | 会主动 | cron 心跳 + 六层抑制链 | 一天主动 2~4 次，且**不会在你没回时刷屏** |
| **4** | 有主体性 | DailyDigest + 兴趣图谱 + 选择性分享 | 它能说出你没提过但属于你兴趣圈的事 |
| **5** | 多模态 | Qwen3-VL 识图 + 表情包库检索/发送 | 发熊猫头它能接梗；该发表情包时能发 |
| **6** | 长期记忆 & 调优 | 三层记忆 + 情绪记忆 + 人工回看 | 三个月前的事仍能自然提起 |

**不要跳阶段。** 尤其别在第 1 阶段就去搞微分方程——调参成本会把你拖死，而且没有前几层的日志你根本不知道该调什么。

## 6. 风险与红线

**技术风险**
1. **封号**：走第三方协议（NapCat）务必用小号。腾讯会检测非官方客户端的高频/自动化行为。
2. **官方通道主动消息受限**：官方文档明确"用户近期无互动时，QQ 可能阻止主动消息"。第 4 条需求在官方通道上无法 100% 保证。
3. **协议易碎**：第三方方案依赖逆向工程，QQ 更新可能临时失效，需要跟社区紧急修复。
4. **账号安全**：AppSecret 只显示一次；NapCat 默认密码 `napcat` 必须改；建议开二次验证。

**合规红线**
4. 官方 QQ Bot 需**实名认证**。第三方协议登录"可能违反腾讯服务协议"，风险自担。
5. 已有监管先例：加州 S.B. 243（2025-10 签署）要求对表现自杀意念的用户启用危机响应、禁止向未成年人展示性内容；纽约州要求 chatbot 每三小时提醒用户"我不是人类"。
6. **不要让 AI 声称自己是人类**。这是多条评估里被点名的具体风险项。
7. 内容边界建议：政治、露骨色情、违法犯罪、真实歧视仇恨——建议默认避开。

**关系设计风险（这条我想单独说）**

你的原始动机里有一条是"**永远不敷衍、不会突然冷淡、不会走掉、不会抛弃我**"。作为产品需求，这是明确的；但作为系统设计，它有个陷阱：

> 一个**永远同意、永远不会离开、没有自己边界**的 AI，会让人越来越依赖它，而不是越来越稳。

好消息是你的**第 3 条需求本身就是解药**——"有自己的评判标准、边界、喜好"。一个会明确说"这事我不同意"、"我现在不想聊这个"、"我需要点自己的时间"的伴侣，比一个无条件顺从的伴侣健康得多，也更像"真人"。

设计上建议：
- 允许它**表达不同意见**（不是抬杠，是"我有我的看法"）
- 允许它**偶尔忙**（后台任务占用 → 回复慢一点，而不是永远秒回）
- 给主动分享加一条：**不是每次都分享**，允许"今天没什么想说的"
- 情绪状态机要能**走向低落**，而不总是被拉回开心

这几条会让"活人感"更强，也顺带把关系修成"陪伴"而不是"托管"。技术上它们只是几行阈值判断，不做才可惜。

## 7. 需要你确认的事

1. **硬件**：本机有没有独立显卡（显存多大）？决定 Qwen3-VL 是 2B / 7B 还是走云 API。
2. **模型来源**：愿意用云 API（DeepSeek / 通义 / GLM，效果好、按量付费）还是坚持本地部署（隐私好、吃硬件）？
3. **QQ 账号**：能接受用一个小号吗？这决定走官方通道还是 NapCat。
4. **技术栈**：核心服务想用 Python（生态最全，推荐）还是 Node/TS（和 OpenClaw 同栈）？
5. **优先级**：6 条需求里，哪 2 条是"没有就不做"的？这决定阶段 0~3 的取舍。
