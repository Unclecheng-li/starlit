# 识图问题怎么排查

> 结论先行：**根因是我把取图顺序排反了。** 正确的做法是
> **拿 `file` 去调 NapCat 的 `get_image` 换出真实路径/URL**，
> 而不是去啃消息里那个 `base64` 字段（它会给**被截断的**数据）。

---

## ★ 根因：取图顺序排错了，base64 不该当主路径

### 我是怎么发现的

你说「别人的 QQ AI 都能识图」，这句话提醒了我——**这是个已被解决的问题**，
我不该在 NapCat 内部瞎猜。于是去查官方文档和 NapCat 源码，两处都印证了同一件事。

### 搜索得到的标准做法

**NapCat 官方接口文档**（`POST /get_image`）：

```
请求：{"file": "image_id_123"}
返回：{"data": {"file": "/path/to/image", "url": "http://..."}}
```

**其他 OneBot 库的做法**（napcat-link、ncatbot 都这么写）：
拿到消息里的 `file` 字段 → **调 `get_image` 换出真实下载地址** →
再下载。**全程不需要 base64。**

### 翻 NapCat 源码验证

`napcat.mjs` 里图片段是这么构造的：

```javascript
const y = { file: c, url: h !== "" ? h : c, file_size: f, file_name: m };
if (configData.enableLocalFile2Url && c) {
    y.base64 = await Lt.readFile(c, "base64");   // ← 读的是完整文件
}
```

**`readFile(c, "base64")` 没有任何截断。** 而 `c` 就是它下载好的**本地完整文件路径**。

### 那我到底错在哪

原来的顺序：

```
1. base64        ← 我把它排第一，理由「零网络、必然可用」
2. 本地路径
3. 远程 URL
```

**这个假设是错的，而且正好是元凶。**

- base64 排在第一个，于是**它一被截断，整条链就用上残图**，根本不会往下试
- 更糟：我当时还写了「拿到非空数据就算成功」——第一个候选有 32KB 就用了
- `get_image` 这个**官方主路径**，我压根没调，只当成最后的兜底

正确顺序应该是：

```
1. file → NapCat get_image 换出的真实路径/URL   ← 官方做法，最可靠
2. 本地路径
3. 远程 URL（要带 Referer，QQ CDN 需要）
4. base64                                        ← 垫底
```

### 已修

- `image_candidates()`：**base64 从第一挪到最后**，本地路径提到最前
- `load_first_image()`：**先调 `get_image`**（不再是兜底），再退到消息段候选
- `get_image` 的 `file` / `file_id` 两个参数名都试（NapCat 2.2.30+ 起可同值）
- 远程下载补上 **`Referer: https://im.qq.com/`**（QQ CDN 不带 Referer 常 403）

验证（假 NapCat 提供完整图，候选里塞一个截断的 base64）：

```
[perceive] get_image 拿到完整图（80 bytes）
  ✓ 优先走 get_image，拿到完整图
  ✓ 没在截断的 base64 上浪费模型调用
  ✓ 下载远程图时带了 Referer（QQ CDN 需要）
```

## 顺带修掉一个真 bug：字符串消息会让服务崩

`_dispatch` 里 `has_img_seg` / `now` 只在「消息是数组」的分支里赋值，
但下面无条件读它。**CQ 码字符串形式的消息一进来就 `UnboundLocalError`。**

这个 bug 在改完顺序后跑验收测试当场炸出来：

```
File "app/channel/napcat.py", line 480, in _dispatch
    if has_img_seg:
UnboundLocalError: cannot access local variable 'has_img_seg'
```

已改成在分支外初始化。**这是"改完必须跑全量测试"的又一个价值证明。**

## 之前那两轮排查（仍然有效，是铺垫）

### 图片数据被截断了（这是真实现象）

落盘的失败图：

```
06a563a6.png: 32768 bytes → PNG 缺少 IEND（IDAT 声明 32768，实际 32723）
f20a8e03.gif: 32768 bytes → GIF 缺少结束标记 0x3B
```

**32768（正好 32KB）**——所以确实有截断发生。既然 NapCat 的 `readFile` 没截断，
那这个截断在别处（可能是 WS 载荷送达我们这边时），**但这已经不重要了**：
只要走 `get_image` 拿到本地路径，就绕开了整条 base64 链路。

### 图片类型（mime）靠猜

同一张 GIF 只改 mime，模型描述的内容完全不同（`image/gif` 说「气鼓鼓」，
`image/png` 说「猫娘被摸头」）。**错的时候模型不报错，会一本正经描述另一张图。**
现在按文件头（魔数）判定，不信任何声明。

### 完整性校验

每个来源都过 `image_complete()`（PNG 查 IEND、JPEG 查 FFD9、GIF 查 0x3B、
WEBP 查 RIFF 长度；**认不出的格式放行**，避免误杀）。不完整就继续试下一个。

## 再看日志怎么读

```
[perceive] get_image 拿到完整图（248193 bytes）        ← 最理想
[perceive] get_image 没取到（file=...），改用消息段里的候选
[perceive] 候选 1/3 不完整（base64，32768 bytes）：...  ← 会继续试下一个
[main] 图片取到了（来源：napcat/get_image (xxx)，类型 image/gif，248193 bytes）
[main] 字节数吻合（248193）—— 数据完整                  ← 与 NapCat 声明的比对
```

| 看到什么 | 含义 |
|---|---|
| `get_image 拿到完整图` | 走对了，正常 |
| `get_image 没取到` | NapCat 接口没应答/file 无效 → 会退回候选 |
| `候选 N/M 不完整` | 那个来源是残图 → 自动跳过 |
| `⚠️⚠️ 截断确认` | 与 NapCat 声明的大小对不上 |
| `⚠️ 识图失败` | 数据完整但模型调用出错 → 看异常 |
